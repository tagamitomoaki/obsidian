# 結論

この保守体制なら、**HPE Networking Instant Onを選びます**。

構成は、HGWをルーターとして残し、Instant OnのPoEスイッチと天井APだけを接続する形です。

決め手は管理画面の簡単さではありません。**家庭内ネットワークから、追加のルーター兼コントローラーという障害点を一つ除去できること**です。

UniFiを簡素化すれば、工務店代表が一次対応できる範囲までは下げられます。しかし、専門保守なしの恒久運用としては、Instant Onの方が構成上の失敗余地が少なくなります。

## 1. UniFiの「守りの設計」はどこまで有効か

提示された設計は有効です。

次の条件をすべて守れば、UCG故障時の暫定復旧は可能です。

- APとスイッチをVLANなしの単一LANにする
- HGWのDHCPサーバーを停止しない
- APとスイッチの管理IPをDHCP取得にする
- 通常時は `HGW → UCG → PoEスイッチ → AP` と接続する
- 障害時は `HGW → PoEスイッチ → AP` に変更する
- 差し替えるポートとケーブルを色・番号で固定する
- 差し替え後、端末のWi-Fi再接続またはAP再起動を手順に含める

UniFi APは設定をローカルに保持するため、コントローラーやゲートウェイが停止しても、既存SSIDそのものが直ちに消えるわけではありません。

ただし、「ケーブルを差し替えるだけで必ず即時復旧」という表現は正確ではありません。DHCPリースの更新、端末の再接続、APの管理IP変更などがあり、復旧まで数分程度の操作が必要になる場合があります。

また、HGW配下にUCGをルーターとして置くと、次の問題が残ります。

- 二重NATになりやすい
- IPv6、VPN、ポート開放、ゲーム機などの不具合原因が増える
- 「HGW側かUCG側か」という切り分けが必要になる
- UCGの設定変更やアップデート失敗がインターネット全体に影響する
- UCGを入れても、MAP-E・DS-Liteなどの回線固有問題をUCG側では解決していない
- UniFiゲートウェイの高度な機能を、VLANなし・単一LANではほとんど利用しない

つまり、この構成では、**UCGの価値を抑制しながら、UCGの故障点だけは追加する**ことになります。

### 「ちょっと詳しい代表」が対応できる範囲

対応可能なのは、あらかじめ手順化できる一次復旧です。

- 電源状態の確認
- ケーブル差し替え
- HGW、スイッチ、APの順次再起動
- UniFi画面でオフライン機器を確認
- バックアップからの復元
- UCG交換後の基本的な再導入

一方、次の対応は不安定です。

- DHCP、NAT、IPv6の切り分け
- UniFi機器のAdoption失敗
- ファームウェア更新後の不具合判定
- バックアップが復元できない場合の再構築
- PoE、配線、AP、スイッチのどこが原因かという切り分け
- クラウドアカウントや所有権移管の問題
- カメラ追加後のストレージ、通知、遠隔アクセス障害

したがって、守りの設計は**障害を直せる設計ではなく、専門家を呼ぶまで基本Wi-Fiへ退避できる設計**です。この体制では、そのためだけにUCGを追加する合理性は弱いと判断します。

## 2. Instant Onを選ぶ決め手

Instant Onなら、構成は次のようになります。

```text
光回線
  │
HGW
  │
Instant On PoEスイッチ
  ├─ AP 1
  ├─ AP 2
  ├─ AP 3
  └─ AP 4
```

ルーター障害はHGW、無線障害はInstant Onという境界になります。

工務店代表が見る対象も、原則として次の三つだけです。

1. HGWがインターネットへ接続できているか
2. スイッチが動作しているか
3. APがオンラインか

UniFi簡素構成では、この間にUCGが入り、調査対象が四つになります。この差が決め手です。

Instant On 1930はモバイルアプリ、クラウドポータル、ローカルWeb GUIによる管理に対応しています。[HPEの導入ガイド](https://community.instant-on.hpe.com/blogs/jamie-easly1/2020/06/03/aruba-instant-on-1930-installation-and-getting-started-guide?hlmlt=VT)

### UniFiへの憧れをどう説明するか

説明すべきなのは、ブランドの優劣ではなく、note記事との前提差です。

> note記事の構成は、ネットワーク、カメラ、録画、ドアベルを一つの管理基盤に集約する構成です。今回は、その管理基盤を保守できる担当者がいません。  
> 機器を同じにしても、保守体制まで同じにはなりません。

UniFiの統合画面は、正常時には分かりやすい一方、障害時にはネットワーク、録画装置、ストレージ、アカウント、通知まで同じ管理系統に集まります。

今回優先すべきなのは「一つの画面に統合されていること」ではなく、**故障時に原因となり得る機器を減らすこと**です。

## 3. 将来のUniFiカメラ・ドアベル

将来UniFi Protectを導入する場合でも、現在のLANをUniFiで統一しておくことは必須ではありません。

拡張時には、既存のInstant Onネットワークへ次を追加できます。

```text
HGW
  │
Instant On PoEスイッチ
  ├─ Instant On AP
  ├─ UniFi Protectコンソール
  ├─ UniFiカメラ
  └─ UniFiドアベル関連機器
```

Protect用コンソールとカメラは、他社製スイッチ・APが存在するLANでも使用できます。ただし、製品の国内提供状況、ドアベルの電源方式、録画容量、PoE必要量は導入時に再確認が必要です。

将来の選択肢は三つあります。

- Wi-FiはInstant Onのまま、監視設備だけUniFi Protectを追加する
- カメラ導入時にスイッチだけPoE容量の大きい製品へ交換する
- 専門保守担当を確保した時点で、ネットワーク全体をUniFiへ移行する

CAT6Aスター配線、天井AP配線、空配管が確定しているため、将来移行の支配的なコストは機器交換です。建物側をやり直す必要はありません。

最初からUniFiにする価値が生じるのは、次のどちらかが確定した場合です。

- 入居時からカメラ・録画・ドアベルまで導入する
- UniFiを継続管理できる業者または担当者を決める

「将来導入するかもしれない」だけでは、現在の保守難度を上げる理由になりません。

1930 JL683Bは24個の1GbE PoE+ポート、PoE予算195W、4個のSFP/SFP+ポートを備えます。[HPE製品ページ](https://www.hpe.com/jp/ja/instant-on/switches/1930-series.html)

AP22はWi-Fi 6、2×2、最大合計1.2Gbpsのモデルです。[HPE AP22製品ページ](https://www.hpe.com/jp/ja/product-catalog/networking/networking-wireless/pip.hpe-aruba-networking-instant-on-ap22-indoor-access-points.1012977949.html)

AP32ではなくAP22を選ぶ理由は、次の通りです。

- 1930のRJ45ポートは1GbEであり、AP32の2.5GbEポートを活用できない
- 300㎡では、AP一台の最高速度より4台の配置・チャネル設計が重要
- 6GHz帯は壁や床を越える用途に不利
- AP22の方が構成と費用を抑えられる

ただし、AP4台で十分かどうかは面積だけでは断定できません。壁材、床暖房、吹抜け、情報ラック位置によって変わるため、まず4台を設置し、残り2か所は予備配線として残します。入居後の実測で弱い場所があれば5台目を追加します。

初期設定は以下に限定します。

- SSIDは原則1個
- VLANなし
- AP間の有線ローミング構成
- 2.4GHzのチャネル幅は20MHz
- 5GHzは現地電波状況に応じて40MHzまたは80MHz
- 自動ファームウェア更新は即時ではなく保守可能な時間帯
- 施主と工務店代表のアカウントを分離
- HGW、スイッチ、APの再起動順序を紙でラック内に掲示
- AP番号、設置場所、スイッチポート番号を一致させる
- 設定情報と機器シリアル番号を工務店・施主双方で保管

## 次点案

次点は、提示済みの**UniFi簡素構成**です。ただし採用条件は、カメラ・ドアベルを入居時から導入すること、または障害時に有償対応できるUniFi経験者を確保することです。現時点の保守体制だけで選ぶなら、Instant Onです。
