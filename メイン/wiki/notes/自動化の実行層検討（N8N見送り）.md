## 結論: N8N は当面入れない

記事の核である「QUEUE（依頼置き場）→ 自動処理 → 成果物」の非同期ループは、N8N なしで実現できる。実装したもの:

- `メイン/QUEUE/` インボックス + 毎朝7時の定期タスク（wiki-queue-ingest: ingest・指示実行・push まで）
- 週次 lint タスク（wiki-weekly-lint: 日曜20時）

N8N を見送った理由（→ [[開発原則]] に整合）:

1. **クレデンシャルの増殖**: N8N に freee や WordPress の認証情報をもう1箇所置くことになり、攻撃面が増える。クレデンシャル最小化の方針に反する
2. **保守対象の増加**: セルフホストなら常駐プロセスの面倒、クラウドなら月額課金。得られる機能の大半は既存手段で足りる
3. **既に持っている代替**: 定常実行は Claude Code スケジュールタスク、Web アプリ側の定時処理は [[Yamasemi]] の Vercel Cron に実績がある

## 再検討のトリガー

- **PC オフでも動いてほしい定常処理**が具体的に現れたとき（スケジュールタスクはアプリ起動中しか動かない。閉じていた場合は次回起動時に実行）
- **外部イベント起点**（メール受信・フォーム送信・LINE 等の Webhook → 自動取込）が必要になったとき

そのときの候補は N8N のほか、Vercel Cron / GitHub Actions（リポジトリは GitHub にあるため、cloud 側で clone → 処理 → push する構成も可能）。
