# Codex と Claude の情報共有運用

Codex と Claude の間で共有すべきものは、チャット履歴そのものではなく、再検証できる成果物と判断履歴である。
両者は同じリポジトリを読み、共通規約、wiki、Git 履歴を介して非同期に引き継ぐ。

## 正本

| 情報 | 正本 | 更新条件 |
|---|---|---|
| wiki の構造・所有権・処理手順 | リポジトリ直下の `CLAUDE.md` | ユーザーと合意したスキーマ変更時 |
| Codex の入口 | リポジトリ直下の `AGENTS.md` | Codex 固有の読込・引継ぎ規則が変わった時 |
| 蓄積された知識 | `メイン/wiki/` | ingest、保存価値のある query、lint の反映時 |
| 内容別の探索入口 | `メイン/index.md` | wiki ページの追加・役割変更時 |
| 変更の時系列 | `メイン/log.md` | wiki に意味のある変更を加えた時 |
| 元資料 | `メイン/raw/` | ユーザーが追加する。LLM は変更しない |

`CLAUDE.md` を共通規約の正本とし、`AGENTS.md` は Codex にその正本を読ませる入口に限定する。
同じ規約を二重記載すると差分が生まれるため、原則として複製しない。

## 引継ぎ単位

一つの作業を別エージェントへ渡すときは、次の5点を残す。

1. 目的: 何を成立させる作業か
2. 変更: どのファイルを、なぜ変更したか
3. 根拠: raw ファイル、wiki の source ページ、一次ソースのどれに基づくか
4. 検証: 実行した lint、test、build、リンク確認とその結果
5. 未解決: 判断待ち、未確認情報、既知の失敗条件

「作業した」「確認した」だけでは引継ぎにならない。
次のエージェントが同じ探索を繰り返さず、かつ結論を再検証できる粒度を残す。

## 実装とレビュー

[[AI協業開発体制]] の原則に従い、実装者だけでレビューを完結させない。
レビュー担当は、コード差分だけでなく目的、前提、検証結果を受け取り、具体的な失敗シナリオを仮説として提示する。
指摘はそのまま事実扱いせず、再現または一次ソースとの照合後に反映する。

## wiki への保存境界

保存する:

- 後の判断で再利用できる設計判断と、その採用・不採用理由
- 複数ソースを横断した比較、矛盾、発見
- 再発防止に使える失敗条件と検証方法
- プロジェクトをまたいで使える運用知識

保存しない:

- 一時的な進捗報告、挨拶、雑談
- 根拠を追跡できない推測
- シークレット、認証情報、顧客個人情報
- raw の全文複製

## セッション開始時の読込順

1. `CLAUDE.md` または `AGENTS.md`
2. `メイン/index.md`
3. 関連する wiki ページ
4. 必要な場合だけ `メイン/raw/` の元資料
5. `メイン/log.md` の直近エントリ

この順序により、規約、現在の整理結果、根拠、直近変更を分離して読む。

## Yamasemi とのリポジトリ間同期

Yamasemi のコード、GitHub Issue / PR、handoff は開発状態の正本であり、この wiki はそこから蒸留した再利用可能な知識を保持する。
軽微なコード変更や途中経過は Yamasemi 側だけに残し、設計判断、業務仕様、データモデル、重要障害、マイルストーン、長期の未解決事項を wiki へ同期する。

Yamasemi 側から wiki の場所を解決するときは、`OBSIDIAN_WIKI_ROOT` 環境変数を優先し、未設定なら兄弟ディレクトリ `../obsidian` を候補とする。
候補が利用できない場合は別のパスを推測して書き込まず、Yamasemi の checkpoint / PR に更新候補を残す。
二つは別 Git リポジトリなので、差分確認、commit、push、失敗管理も分離する。
